# OpenBao production runbook

Status: written 2026-10-24 from the owner's decisions 16 to 27 (see `docs/PREMODULES_PLAN.md`, "Decisions recorded"). The framework
provides the client, the policies and the generated deployment assets (`modulus add-openbao`, `deploy/openbao`). It does not build or run
OpenBao. Every step marked **Operator** is run by whoever runs the infrastructure, and is not verified by the repository.

Check every command below against the OpenBao version you deploy. The command names follow the OpenBao CLI (`bao`).

## 1. What the framework does and does not do

| Area | Framework | Operator |
|---|---|---|
| Client, read-only runtime identity, cached reads | Built (`Synvro.Modulus.Secrets.OpenBao`, `CachedSecretStore`) | Configure the address and the AppRole |
| Provisioning host (only writer) | Generated by `modulus add-openbao --provisioner` | Hold the provisioner AppRole |
| Policies | Generated in `deploy/openbao` | Apply them to the server |
| Raft, TLS, unseal, snapshots, audit devices | Not built | Run and test them |
| Recovery shares, break-glass, human SSO and MFA | Not built | Decide, store and test |

## 2. Final choices (owner decisions 16 to 27)

- **Deployment (16):** Podman on Linux, with a dedicated OpenBao service. Auth: AppRole, with machine credentials delivered securely.
- **Availability (17):** three independent Raft nodes in production. Quorum is two of three. The nodes sit on separate hosts and, where
  possible, in separate failure domains. Three containers on one VPS are not high availability. One node is acceptable only for development
  or a temporary pilot.
- **Unseal (18):** manual Shamir recovery shares until a KMS is configured. Shares are held by separate custodians and never kept with the
  running service.
- **Secrets (19):** database credentials, tenant credentials, payment and API keys, webhook secrets, LDAP and SAML bind credentials, AI
  platform keys, Data Protection keys, personal-data search keys and log-redaction keys.
- **Database credentials (20):** static KV secrets with a controlled rotation schedule. Dynamic credentials are revisited later.
- **Outage (21):** reads may use a cached secret for at most five minutes (`Secrets:Ttl` and `Secrets:MaxStaleOnFailure`, both 5 minutes by
  default). Writes that need unavailable credentials, and new-tenant provisioning, fail closed.
- **Tenant database model (22):** the shared database is the default. Tenant scope is enforced in the application and by row-level security
  where the database supports it. Per-tenant credentials alone do not isolate rows. Database-per-tenant where required.
- **Human access (23):** SSO and OIDC with MFA for administrators. A separate break-glass account, independent of SSO.
- **Audit destination (24):** OpenBao audit events go to independent, access-restricted storage, not only the OpenBao host's disk.
- **Environments (25):** production OpenBao is a separate instance from development and staging. Distinct identities and policies per
  environment.
- **Python (26):** no Python client until a deployed Python service needs these secrets.
- **Rotation (27):** database passwords and API or payment keys every 90 days, or sooner if a provider requires it. AppRole Secret IDs are
  short-lived and issued per deployment or provisioning event.

## 3. Deployment on Podman (Operator)

1. Run OpenBao on its own host or VM, not on the API host.
2. Use a published, pinned image, and record the version in the deployment inventory.
3. Give the container a persistent volume for Raft data, owned by a non-root user, and restrict its permissions.
4. Terminate TLS with a certificate from your CA. Accept connections only from the API hosts, the provisioning host and administrators.
5. Keep the listener on a private network. Do not expose it to the internet.

## 4. High availability (Operator)

1. Deploy three nodes on three hosts. Give each its own Raft storage.
2. Initialise the first node, then join the other two with `bao operator raft join`.
3. Check the cluster with `bao operator raft list-peers`. All three must be voters.
4. Take snapshots on a schedule with `bao operator raft snapshot save`. Store them encrypted, away from the cluster.
5. Losing one node keeps the cluster available. Losing two stops writes until quorum returns. Plan for that in the on-call procedure.

## 5. Unseal and recovery (Operator)

1. Initialise once with five key shares and a threshold of three: `bao operator init -key-shares=5 -key-threshold=3`.
2. Give each share to a different custodian. Record who holds which share, outside the cluster.
3. Never store the root token beside the service. Revoke it after the initial setup and use it only for break-glass.
4. Test recovery at least once per year: restore a snapshot into an isolated cluster and unseal it with three custodians.
5. Move to an external KMS when one is available, and document the change.

## 6. Authentication and policies (Operator, with generated files)

- The API host's identity is read-only. Its policy is `deploy/openbao/runtime-read.hcl` (generated by `add-openbao`).
- The provisioning host is the only writer. Its policy is `deploy/openbao/provisioner.hcl`, and it has its own AppRole.
- Create one AppRole per application and per environment. Do not reuse a role across environments.
- Issue Secret IDs with a short lifetime and limited use, for example:
  `bao write auth/approle/role/<role> token_policies=<policy> secret_id_ttl=24h secret_id_num_uses=1`.
  Reissue them on every deployment. Do not leave a long-lived Secret ID in configuration.
- The role ID is not a secret, but it is kept with the deployment configuration. Deliver the Secret ID through the deployment step, not
  through the repository.
- Never use the root token for application requests.

## 7. Human access and break-glass (Operator)

- Administrators sign in through the chosen SSO provider (OIDC) with MFA. Confirm the provider supports the OpenBao OIDC flow you use.
- Keep one emergency account, outside SSO, with its own recovery material held by two people.
- Review who can use the emergency account every quarter. Test the procedure at least once a year.
- Every privileged action is audited (section 8).

## 8. Audit (Operator)

1. Enable a file audit device that writes to local disk: `bao audit enable file file_path=<path>`.
2. Forward the audit file to independent, access-restricted storage, and check that the forwarding works.
3. Set a retention period for the audit files. Do not delete audit files inside that period.
4. Alert on audit device failures. OpenBao is expected to refuse requests when no audit device can write (per its documentation; verify on your version).

## 9. Cache and outage behaviour (framework, verified 2026-10-24)

- Fresh values are served for `Secrets:Ttl` (default 5 minutes).
- While OpenBao is unreachable, a cached value is served only until `Secrets:MaxStaleOnFailure` after it was fetched (default 5 minutes).
  After that the request fails with `503`.
- The cache serves reads only. Writes go to the provisioning host, which needs a live OpenBao connection. This is the intended behaviour; it is not verified by a test in this repository.
- The OpenBao health check reports `Degraded` (not `Unhealthy`) while cached secrets are being served.
- Rotation and the cache window interact. A rotated secret reaches the application within `Secrets:Ttl`. Keep the window at 5 minutes.

Unverified: this runbook does not measure the end-to-end behaviour under a real OpenBao outage. Test it in staging before go-live (section 11).

## 10. Rotation (Operator)

| Secret | Schedule | Method |
|---|---|---|
| Database passwords | Every 90 days | KV rotation, then restart or reconnect the connection pool |
| API and payment keys | Every 90 days, or sooner if the provider requires | KV rotation |
| AppRole Secret IDs | Per deployment, short lifetime | Reissue, do not extend |
| Data Protection key ring | Per your key policy | Keep old keys until data encrypted under them is re-encrypted |

Coordinate rotation with the five-minute cache window, so the old value is not used after the new one is live.

## 11. Go-live checks (Operator)

- [ ] Three Raft voters, all healthy, with a tested snapshot restore.
- [ ] Unseal shares held by different custodians, with a documented list.
- [ ] Audit device writing to protected storage, and forwarding confirmed.
- [ ] Each application uses its own AppRole in production. No root token in use.
- [ ] Outage test in staging: stop OpenBao, confirm cached reads for at most five minutes, then `503`, and writes refused.
- [ ] Rotation test in staging for one database password and one API key.
- [ ] Break-glass account tested, and its recovery material confirmed.

## 12. Open items (operator)

- Choose the SSO provider and confirm its OpenBao OIDC support.
- Choose the KMS for auto-unseal, when one is available.
- Name the custodians for the five unseal shares.
- Set the retention period for OpenBao audit files.
- Decide the environment hosts and their failure domains.
