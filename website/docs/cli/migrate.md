# modulus migrate

Database migration commands. Works with both EF Core and dbsh engines.

## Usage

```bash
modulus migrate add <Name> [options]
modulus migrate update [options]
```

## migrate add

Scaffolds a new migration. The command auto-detects the engine per module:

- **EF Core modules** — runs `dotnet ef migrations add` in the module's
  Infrastructure project, producing C# migration files in `Infrastructure/Migrations/`.
- **dbsh modules** — runs `dbsh create --name {Name} --type schema --module {Module}`
  from the module's Infrastructure directory, producing a SQL stub in
  `Database/Migrations/{Module}/`.

### Options

| Option | Description |
|--------|-------------|
| `--module` | Specific module (default: all) |
| `-o, --output` | App root directory (default: current dir) |

### Examples

```bash
# Add migration to all modules
modulus migrate add InitialCreate

# Add migration to a specific module
modulus migrate add AddProductsTable --module Catalog
```

### Migration Name Rules

Names must contain only letters, digits, and underscores
(pattern: `^[A-Za-z0-9_]+$`). Names like `Add-Products` or
`Initial Create` are rejected.

### dbsh-specific Behavior

When the target module uses dbsh, the CLI:

1. Changes to the module's Infrastructure directory
2. Runs `dbsh create --name {Name} --type schema --module {ModuleName}`
3. Produces `Database/Migrations/{ModuleName}/{seq}_{Name}.sql`

This is a stub — you fill in the SQL by hand.

## migrate update

Applies pending migrations to each module's database.

### Options

| Option | Description |
|--------|-------------|
| `--module` | Specific module (default: all) |
| `-o, --output` | App root directory (default: current dir) |

### Examples

```bash
# Update all modules
modulus migrate update

# Update a specific module
modulus migrate update --module Catalog
```

### What It Does Per Engine

**EF Core modules:**

```bash
dotnet ef database update --project <module.csproj> --startup-project <host.csproj>
```

**dbsh modules:**

```bash
dbsh init <infra-dir>       # idempotent: create tracking tables if missing
dbsh migrate --yes <infra-dir>  # apply pending .sql files
```

The CLI warns when `{MODULE}_CONNECTION` is not set — dbsh falls back to
the connection in `migration.json`. On a fresh database, `dbsh init` must
run first; the CLI handles this automatically.

### Engine Detection

The CLI detects whether a module uses dbsh by checking for the marker file
`Database/Config/migration.json` inside the module's Infrastructure project.
This file is generated by `modulus app --migration-engine dbsh` or
`modulus add-module --migration-engine dbsh`.

When `--module` is omitted, every module is processed — each using its
own engine.

## Automatic Migrations at Startup

```csharp
// Program.cs
await app.Services.MigrateModulusDatabasesAsync();
```

| Mode | Behavior |
|------|----------|
| `MigrateOrCreate` (default) | `Migrate()` when migrations exist, else `EnsureCreated()` |
| `Migrate` | Always applies migrations; throws if none |
| `EnsureCreated` | Snapshot only; no migration history |

dbsh modules are **skipped** by `MigrateModulusDatabasesAsync` — they are
marked via `ExternallyManaged<TContext>` so the startup doesn't conflict
with the dbsh tool.
